# 翻譯自我改善

將指定期間的翻譯記錄轉成可驗證的程式改善。預設執行已授權的步驟 1～5；第 5 步完成後交付人工複測文件、通知使用者並結束本輪工作，等待人工結果後才承接第 7 步。

## 啟動與現行來源

1. 從工作區向上定位本專案的 `AGENTS.md`，先讀 [總覽核心規則](../../../docs/系統規則與知識總覽.md#1-工作前必讀與文件維護)，再依任務索引讀相關章節；同任務未變資料不重讀。
2. 主 Agent 核對既有異動、有效授權、停修與未解 findings；依 [Codex 開發流程](../../../docs/Codex開發流程.md) 保留單一應用寫入責任、真實 NMT 與部署門檻。
3. 先讀 [階段與交接契約](references/stage-contracts.md)，建立一個 runId 及 Git 忽略的 `.local/translation-improvement/{runId}/`。每個 runId 表示一份實質工作；候選更名不重置根因輪次、字元累計或限制。
4. 記錄指定 PRD 群組、日期、台北時區、固定查詢截止時間、候選範圍及允許動作。群組／期間沿用對話；只有實質缺項才詢問。未指定排程不自行設定週期或建立 automation。
5. 使用者只要求分析時交付第 1 步。使用者明確要求「執行自我改善到 DEV／步驟 5」時，依所確認的範圍承接分析、計畫、開發、既有 DEV NMT 及 DEV 部署，不逐步重問已授權動作。建立或閱讀 Skill 本身不授權執行這些雲端動作；既有付費暫停與停修限制須另外核對。

## 主 Agent 控管與角色深度

主 Agent 負責範圍、授權、資料匯出、文件落盤、派工、候選凍結、階段核准、部署與使用者通知。依本 Skill 執行完整改善是使用者指定的分步派工流程；其他任務繼續使用專案最小必要角色原則。

| 步驟 | 負責角色 | 模型與推理深度 | 交付文件 |
|---|---|---|---|
| 1. 找出案例並判斷可修正性 | planner | GPT-6.1 Sol／high | `01-analysis.md` |
| 2. 修改計畫與環境準備 | 同一 planner | GPT-6.1 Sol／high | `02-plan.md` |
| 3. 開發及本機檢查 | implementer | GPT-6.1 Sol／high | `03-development.md` |
| 4. 獨立驗證及真實 DEV NMT | verifier | GPT-6.1 Sol／high | `04-verification.md` |
| 5. DEV 隔離封裝及部署 | 主 Agent 執行；同一 verifier 核對候選及部署證據 | 主 Agent 沿任務／UI，建議 high；verifier 為 Sol／high | `05-dev-deployment.md`，另產生 `06-human-review.md` 待使用者填覆 |
| 6. 人工複測 | 使用者；主 Agent 整理結果 | 人工判定；主 Agent 沿任務／UI | `06-human-review.md` |
| 7. PRD 適配、核對及發布 | 主 Agent 執行；同一 verifier 核對發布範圍 | 主 Agent 沿任務／UI，建議 high；verifier 為 Sol／high | `07-prd-deployment.md` |

- 開工及初次派工核對 `.codex/config.toml` 與相關 `.codex/agents/*.toml` 的實際可取得設定一次；不能確認實際載入值就記為未知，不能把期望設定宣稱為已生效。Skill 不會切換主 Agent 模型或覆寫 UI。
- 跨模組且仍有實質設計歧義、共通契約未收斂或複雜驗證時，選用對應 `planner_xhigh`／`implementer_xhigh`／`verifier_xhigh`，記錄升級原因。一般工作不固定使用 xhigh、max 或 ultra；推理升級不延長兩輪停修上限。
- 用 `collaboration.spawn_agent` 明確設定 `agent_type` 與 `fork_turns="none"`；訊息交代本階段、來源路徑、擁有檔案、驗收、可用權限及必讀核心規則。不要用 `task_name` 冒充角色，也不要建立新的使用者 chat 當作子 Agent。
- 每次交接以約 500 字摘要及證據路徑為目標。planner／verifier 是 read-only，由主 Agent 保存其回傳文件；需要執行或寫出證據時，由子 Agent 指定確切命令，主 Agent 在已授權範圍代跑，記錄實際執行者。
- 同一階段系列沿用角色，必要續作使用 `followup_task`；控制訊息使用 `send_message`，新結果用 `wait_agent` 事件等待。子 Agent 不再派工；對使用者按平台要求回報有意義的進度。
- implementer 是唯一應用寫入者，須知道有人共享工作區並保留他人異動；主 Agent 在其工作期間只控管交接與不重疊操作。verifier 檢查時凍結其範圍，修正後交同一 verifier 複驗，主 Agent 不重做同一份已委派工作。
- 若所需角色不可用，記錄派工缺口；不可宣稱已獨立驗證，也不可默默換角色、模型或引擎完成發布。

## 案例分流與可修正性

分析原文、實送 NMT 輸入、原始 NMT 輸出、還原譯文與最後回覆，按根因分組，而不是按句子各加一條規則。

| 分類 | 處理方式 |
|---|---|
| `PROGRAM_FIXABLE`：保護範圍、還原、格式、誤拒／漏檢或事件處理等可重現程式問題 | 提出共通修正、代表性正反例及退步風險，通過可行性門檻才進入開發。 |
| `NMT_LIMITATION`：偏差已在 raw NMT，沒有安全且可通用的程式方案 | 留作已知品質限制及追蹤案例；不以逐句替換、猜測上下文或增加未授權引擎修補。 |
| `NEEDS_CONTEXT`：原文歧義或上下文不足 | 列出待確認原意；未知不能標為正確或確定錯譯，也不能直接生成修正規則。 |
| `NO_OBVIOUS_ISSUE`：本次比對未見明顯問題 | 作為觀察或回歸對照；不宣稱完整語意正確。 |

raw NMT 有偏差並不自動排除程式問題：先確認程式保護與實送格式是否造成偏差；只有具體、可驗證且符合現行契約的修正才列 `PROGRAM_FIXABLE`。能寫出較好譯文不等於已找到程式修正方案。

若全部案例只屬 NMT 限制、歧義或未見問題，主 Agent 保存分析，標記 `NO_CODE_CHANGE`，步驟 2～5 為 `NOT_APPLICABLE` 並通知使用者；不得為完成步驟數而開發、呼叫 NMT 或部署。

## 執行門檻

- 核心流程保持：原文 → 保護必要原樣片段 → 既有固定 Google NMT → 原樣片段完整性檢查 → LINE。不自行接 glossary、Gemini、其他引擎或完整語意 guard。
- PRD 記錄及真人內容只存 Git 忽略的 `.local/`，報告不外洩 Secret、userId 映射或未授權交談；通知使用者時給必要摘要與私密本機檔案連結。記錄讀取不擴大為真人原文外送授權，依有效測試資料授權用原案例或能重現問題的合成／去識別案例，並說明替代資料的驗證限制。
- 計畫先列既有 Firestore、Logging、DEV Translation 及部署入口所需服務／API、身分、專案與可用性；開发或驗證發現缺項先回計畫處理，不當場新增服務或啟用 API。
- 每輪核心翻譯驗證及修正複驗，使用同一份 manifest 真正送入當前凍結應用的既有 DEV NMT；所有 Agent、基準、候選及對照實送 contents 合計最多 10,000 Unicode 碼點，含保護標記及所有空白。送前預留，可能已送出的失敗／逾時不退回預留量；LINE 用測試替身，真人複測另列。
- mock／歷史回應只作輔助；缺當輪真實證據標 `VERIFICATION_INCOMPLETE`。首次系統性失敗先檢討共通契約；同根因兩輪未收斂停止修補，版本更名及角色深度升級不能重置。
- 有效交付須有必要完整離線、包內及 predeploy 檢查。DEV 按 [封裝工具](../../../docs/DEV部署封裝工具.md) 新建隔離包並原樣保留指定 dotenv／別名（含 Wei）；PRD 按 [現行發布來源](../../../docs/PRD最新NMT部署20261005.md) 的正式適配及部署保護。兩者都不能直接從主工作區發布。

## 第 5 步交付與人工關卡

只有實際 DEV 部署、版本／流量／來源核對及相關部署後檢查完成，才將第 5 步記為完成。主 Agent 更新 `run-state.json` 為 `WAITING_HUMAN`，保存待驗收的 DEV revision、凍結包 hash、有效證據範圍及未解問題，生成 `06-human-review.md`。

向使用者通知：已部署的 DEV 版本、改善項目、人工測試步驟／預期、文件連結及仍未通過範圍；接著結束本輪，等待使用者人工測試。這個等待是本機流程狀態，不呼叫目標工具把未要求暫停的 goal 標為 paused，也不自行安排提醒或長時間輪詢。

- 使用者確認當前 DEV 版本「人工測試通過，繼續下一步」即可承接已約定的第 7 步 PRD，不重複詢問相同授權。只說「已測試」、未提供通過結果、沒有回覆或等待時間經過，均不算通過。
- 回報失敗就記錄證據、回到第 2／3 步及同一 verifier 複驗；若重部署 DEV，更新版本並重新等待該版本的人工複測。兩輪停修限制仍維持。
- 人工結果若無法對應當前候選，先核對版本；版本、設定或有效驗收範圍變動須重驗受影響部分，不能沿用舊版本人工 PASS 當成新版本通過。
- 第 7 步仍須核對當前來源、PRD 隔離設定、既有未解項目及正式 predeploy 門檻。若有 PRD 專屬程式修改，回到開發及獨立驗證，影響核心時完成新的當輪 DEV NMT；原人工結果僅沿用未變且適用的範圍。
- Skill 僅定義流程與交接，並非已建排程或雲端操作工具。即時工具／auto-review 限制仍有效；遇拒絕說明被拒動作與原因，交付不受影響部分，不繞過限制或把未完成操作記為成功。
