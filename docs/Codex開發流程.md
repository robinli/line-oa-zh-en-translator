# Codex 開發流程

最後更新：2026-10-08。

本文件是本專案的現行開發規範。先讀 [總覽核心規則](系統規則與知識總覽.md#1-工作前必讀與文件維護)，再按任務閱讀相關章節；工作與修訂紀錄集中在 [專案日誌](專案日誌.md)。

## 1. 選擇最小必要流程

核心基準為原文 → 必要原樣保護 → NMT → 片段／段落檢查；中英、中越依 SOL_REVIEW_ENABLED 共用 Sol 評審及必要時原文單次重譯，重譯再作字面核對後送 LINE，不作第二次評審。OK 使用 NMT，NOT_GOOD／UNCERTAIN 或完整非空 NMT 的片段／段落拒絕才重譯；API、缺項／空白回應及 Sol／重譯檢查故障沿用 🚧。預設開關關閉，本機結果不呼叫模型。開啟時中英、中越都以 receipt+40秒為處理界線，共用50秒批次操作期限及 DeadlineScope。中越只保護 native、代碼及明確片語，不套用中英商務人名／條件政策。 契約、環境生效與人工驗收見 [中越 Sol 整合與 DEV 發布](中越Sol評審與DEV發布20261029.md)；不新增 GCP 服務。

- 問答、文件、格式與 Agent 設定由主 Agent 處理及檢查。
- 一般程式修改：主 Agent 規劃與實作 → 一位 verifier 獨立驗證 → 原實作者定向修正 → 同一 verifier 複驗。
- 使用者指定 [翻譯自我改善 Skill](../.agents/skills/translation-self-improvement/SKILL.md) 的完整流程時，依該專用分步派工與文件交接執行，標準 Sol／high、必要時對應 xhigh，主 Agent 控管至 DEV 部署並通知人工複測；確認該版本通過且要求繼續後才承接 PRD。僅有 NMT 品質限制或歧義時不強行進入開發，單一應用寫入者與下列驗證／授權規則維持。
- 已有完整可執行計畫且範圍未變時直接沿用；只有重大未解設計、原方案失效或重要需求變更才考慮 planner。需要獨立實作責任時才加入 implementer；各角色須有具體範圍，一次只有一位程式寫入負責人。
- 依可獨立驗收的成果分階段，列出範圍、可觀察行為、驗收與停止條件；已通過者及時交付，繼續其餘已授權工作。
- 主 Agent 不重做已委派的分析或實作；必要證據不足時保留未完成狀態，驗收門檻不因成本或輪次降低。

## 2. 模型與正確派工

[專案設定](../.codex/config.toml) 主模型為 `gpt-6.1-sol`，主 Agent 推理沿用任務／UI 選擇，未指定的一般開發建議 High；標準子角色固定 Sol／high，困難任務才明確選用 xHigh。

| 職責 | 標準角色 | 困難任務角色 | 權限 |
|---|---|---|---|
| 規劃 | planner | planner_xhigh | read-only |
| 實作 | implementer | implementer_xhigh | workspace-write |
| 獨立驗證 | verifier | verifier_xhigh | read-only |

- 派工明確指定 `agent_type`；`task_name` 只作名稱。預設 `fork_turns="none"`，交代原需求、檔案責任、驗收、最新 findings 與證據位置。
- 並行上限為 4 個子 Agent，按必要工作啟動；High／xHigh 是同職責的選項。
- 角色檔須有 name、description、developer_instructions，名稱與派工角色一致；模型 ID 與推理強度分開設定。
- 開工、使用者變更模型或初次派工時核對可取得的實際模型／推理一次。無法確認時如實標示並繼續不依賴它的工作；不為確認設定啟動模型驗收。
- 專案預設可能被任務／UI 覆寫；改檔不保證既有任務或已啟動角色重新載入。角色缺少或仍是舊設定時，回報獨立驗證缺口。
- 有關聯的修正沿用同一角色；僅有實質新工作時使用 followup_task，不為查狀態重新啟動角色。

## 3. 控制讀取與協調成本

- 只讀任務相關來源，同一任務未變內容不重讀；工具批次處理獨立讀取，回傳必要片段。
- 初次交接以約 500 字摘要與證據路徑為目標，後續只補新 findings、階段、變更與阻礙；完整命令及日誌留在證據檔。
- 主 Agent 摘要只列當前階段、責任人、凍結範圍與待決事項。等待時可做不重疊工作，使用平台允許的事件等待並簡短回報新進度；未變狀態不額外查詢、催問或重產快照。
- 每任務維護一份證據索引，記錄候選類型、根因輪次、檢查／未解項目、有效授權及下一步；來源 hash 與封存限於有變更或需要交付的範圍。
- 一般開發先忽略翻譯計費；本機測試、mock 與回應重播用於開發及故障注入，verifier 的真實 NMT 驗收仍必須完成。估費、額度盤點及雲端帳本核對不作離線開發前置條件。
- 需要真實翻譯 API 或明確的費用工作時，再按有效授權一次核對範圍、預算、請求／字元與停止條件。已有授權不重複詢問；實際計數、帳本、部署保護及既有暫停維持。

## 4. 實作收斂、分層驗證及付費測試

- **開工前計畫與預檢：** 列明所需既有 GCP 服務／API、專案、用途及可用性，依有效授權完成必要準備；新增服務需求須在計畫階段處理。開發及驗證期間不得新增 GCP 服務或啟用 API。缺依賴先回到計畫處理，不為排錯當場啟用。shell／runtime、必要登入、權限、參數與測試入口一次核對，缺項一次列出；繼續不依賴缺項的本機工作。
- **驗證行為與規則交界：** 先用最小代表性正反例走公開入口、翻譯／還原路徑，覆蓋原失敗、相鄰邊界及新舊規則交界，再擴大實作。明確需求直接納入驗收，僅釐清仍有實質歧義的部分。
- **語意解析完整性：** 涵蓋忠實譯文、責任／否定、標點與連接詞、已知及未知剩餘片段。只有解析完整的範圍才能推定內容缺失；unknown 不等於一致或已知缺失，沿用既有安全政策。方案不足時限縮或留作研究。
- **先確認可行性：** 需要外部服務實際行為時，在必要隔離、計數與授權控制完成後，先測最小高風險集合；mock 或小量結果只支持其驗證範圍。
- **首次系統性失敗先檢討：** 整理共通根因、正反例與方案，再決定修正、限縮或撤回。相同根因連續兩輪修正與獨立複驗仍未收斂時，停止逐案補丁並檢討設計；版本或 finding 改名不重置輪次，停修與授權限制持續有效。
- **本機入口：** Windows 使用 [本機離線檢查](本機離線檢查.md) 的 `scripts/check-local.ps1`，固定 Node 22、工作目錄及測試範圍；缺檔、零測試或非零退出碼均不得視為通過。
- **工具與診斷：** 評估工具保持最小必要功能，保存請求識別、原始回應、必要記帳及防重複控制；依原資料契約記錄安全階段／細碼，不擴大保存 Secret 或身分映射；被拒候選原則不另保存，2026-10-03 使用者明確授權的 DEV 交談 nmtOutputContents 依品質紀錄文件保存 NMT 原始輸出，其他集合與日誌維持原限制。

| 候選類型 | 必要檢查與可宣稱狀態 |
|---|---|
| 研究／可行性 | 驗證代表性正反例與方案；只報已支持範圍 |
| 修正候選 | 凍結受影響範圍，定向測試及必要型別／建置，再交同一 verifier 複驗；涉及核心翻譯流程須完成本輪真實 NMT，重播作輔助 |
| 交付候選 | 穩定後完整離線一次並固定產物、設定預檢與必要當前真實NMT證據；獨立驗證支持範圍，另列未解品質及人工驗收 |
| 部署候選 | 沿用同一已驗證產物與完整證據，核對環境差異、SHA與必要predeploy guard、有效授權及發布後健康；不例行重跑完整集合 |

- 開發迭代按影響範圍跑定向與必要相鄰回歸；穩定候選只完成一次完整離線驗證並固定產物／證據。DEV驗收通過且已授權PRD時，同一應用產物沿用既有證據，主要核對環境差異、來源SHA、必要部署guard與發布後健康，不因DEV→PRD例行重建或全套重測。程式、依賴或實送契約有變，才補受影響檢查；新風險證明需要時才重跑完整集合。 修正PASS只支持其範圍，沒有完整交付證據不能宣稱可部署。
- **Verifier 真實 NMT：** 每輪影響核心翻譯流程的驗證／修正複驗，都由 verifier 設計並執行最小真實 NMT 集合，使用當前凍結應用入口完成保護、NMT、完整性核對及 LINE 回覆內容生成；涵蓋原失敗與相鄰正反例，原文資料依有效授權。LINE 發送用測試替身捕捉，真人手機驗收另列。即使只改輸出檢查／還原而實送參數不變，仍須有本輪真實 NMT；mock／舊回應不能替代。
- **每輪最多 10,000 字元：** 按所有實送 contents 的 Unicode 碼點合計，含英文、標點、空白、換行、HTML／保護標記；合併主／子 Agent、基準／候選及對照請求。使用同一輪 ID、manifest 與累計，送出前預留並核對剩餘量，可能已送出但失敗／逾時的請求保留預留量；不得因改名或拆分 Agent 重置。上限不足就縮小集合；新輪次限於有實質候選修正或新驗收需要，兩輪停修限制持續。
- **授權與缺口：** 使用者本次明確要求 verifier 做既有 DEV NMT 的真實測試，每輪上述上限；在這個範圍內沿用授權，不逐案重複問費用。本次2026-10-08明確計畫另授權 Sol 與 DEV 發布：主 Agent、verifier、部署後共用 US$2／最多32生成請求，失敗／逾時不退預留，PRD 原等 DEV 手機通過且要求繼續；2026-10-08 使用者最新直接「部署PRD」授權本次正式發布，手機驗收仍未確認。舊研究批次、GCP 服務變更及真人 LINE 發送不因此獲授權。服務／權限／資料授權不足或缺本輪實測時，標示 VERIFICATION INCOMPLETE；不得以離線 PASS 宣稱本次故障已解除。
- 沿用回應保留原模型、資料集、請求參數與版本；新程式重播另記版本，不修改原始回應／預期，也不把舊回應改標為新候選 API 結果。
- Verifier 獨立核對需求、diff 與證據，重現關鍵正反例；真實 NMT 證據記錄輪次、凍結來源／建置、request profile、請求與實送字元、原始回應、還原及核對結果。受 read-only 限制時由 verifier 指定確切命令交主 Agent 執行，再獨立評閱 raw 結果並說明執行者；同根因 findings 一次交接，複驗聚焦修正及影響。
- 真實 API 只在有效範圍與預算內執行；全量付費回歸集中於確有必要的穩定候選，不因日期、版本或 hash 改變例行重跑。接近預算上限、重複失敗或需擴大範圍時，停止新增呼叫並說明剩餘工作。
- DEV 封裝原樣保留指定 dotenv 的現有別名（含 Wei），不主動更新或清空；雜湊、DEV 引擎／runtime、隔離及必要部署檢查維持，詳 [封裝工具](DEV部署封裝工具.md)。

## 4.1 同產物沿用與測試分層（2026-10-29）

使用者明確要求縮短DEV與DEV→PRD耗時。本節統一解釋Skill、封裝與部署文件的「必要完整檢查」：要求有效證據，不要求主工作區、隔離包、DEV predeploy及PRD predeploy各自重跑同一全套。

1. 開發期間依diff、呼叫路徑及共通契約，選定向與必要相鄰回歸。穩定後在交付產物上完成一次完整型別／應用／工具／建置驗證，再凍結來源與build、package-lock、Node／工具版本、必要fixture／設定、命令與完整日誌的SHA及候選ID。主Agent完成這份證據後，同一verifier查證關鍵邊界與來源，不重做相同全套。
2. DEV用該凍結產物發布。部署入口仍核對專案／runtime／Secret、dotenv、原設定、去重、有效授權與完整性；可驗證沿用的完整證據，不再掛一份相同npm verify。保留Cloud建置、平台部署及發布後版本／流量／來源／簽章健康檢查，這些與離線回歸不同。
3. DEV人工確認及PRD授權到位後，PRD只作環境封裝差異：正式目標、dotenv／別名、Secret、身分、資源與guard。所有應用來源／build／工具及lock相同就沿用同一驗證與真API證據；環境包可以有自己的manifest，但不能因此重建應用、重新研究、全套重測或自動增加翻譯API。單純promotion不是新核心修正輪次。
4. 程式／依賴、來源build、輸入保護／wire、runtime或外部服務契約有實質變動，先指出證據失效範圍，再補對應檢查。核心翻譯修正仍需當前真DEV NMT；API實際行為有新風險才補最小真實集合。無法證明產物一致或證據有效時不能沿用；必要時才重新完整驗證，須說明原因。
5. 已停用的歷史測試，可在證明沒有現行路由、靜態／動態依賴、共用契約及部署保護依賴後移出必跑集合，保留可追溯封存與清單。不得只因名稱舊、數量多或本次未直接修改就刪除；共用helper與仍被正式路徑使用的歷史規則仍要覆蓋。本次只調整規則，未完成全歷史依賴稽核，也未移除測試。

進度及交付分開列離線回歸數、真實NMT／Sol案數、LINE替身與人工手機結果；離線2415項不等於2415筆真實語意或手機測試。耗時指出離線檢查、封裝／guard、Cloud建置／更新或人工等待，不把所有時間稱為測試。

本次已部署凍結包及舊日誌不改寫。既有工具若仍硬性掛完整verify，下次建立候選時先適配證據沿用與guard；在產物已凍結或發布途中不得臨時刪掉強制命令。本節不宣稱工具已自動提供快取或測試依賴選擇。

## 5. 記錄與生效確認

每階段記錄角色、可確認的模型／推理、版本、檢查範圍、結果及證據路徑；分別報告開發、測試、部署與人工驗收，未解 findings 持續追蹤。需要記錄用量時，Codex token 與翻譯 API 字元分開，推理 token 不重複加總。

文件／格式／設定調整由主 Agent 做內容、連結、TOML（如適用）及 UTF-8／CRLF 靜態檢查，這類工作不啟動 verifier 或 NMT 呼叫。流程與 10,000 字元限制由 Agent 按共用 manifest 執行；此次改文件／角色指示不代表 API 執行工具已有自動限額，也不代表既有對話或角色已重新載入。

設定參考：[角色配置](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[設定欄位](https://learn.chatgpt.com/docs/config-file/config-reference)。

## 6. 開發時需要交代與注意

需求交代目標、DEV／正式範圍、應接受／應拒絕的例子、相容限制及必要操作授權；對話已有資料直接沿用。開發重點是正確輸出是否誤拒、錯誤輸出是否漏放及未知片段如何處理；測試總數僅是證據的一部分。

使用 Node 22、UTF-8／CRLF 與既有本機入口，尊重其他工作區異動。交付已驗證階段時繼續其餘授權工作；新對話、候選更名或階段切分不解除既有 findings、停修、付費暫停或人工驗收要求。
