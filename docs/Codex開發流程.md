# Codex 開發流程

2026-09-25：依昨夜 NMT 開發檢討補強實作收斂、早期可行性驗證及主 Agent 協調；只適用本專案，不代表恢復已暫停的開發、付費翻譯評估或部署。

## 1. 選擇最小必要流程

- 問答、文件、格式、Agent 設定：主 Agent 處理及檢查，不建立子 Agent。
- 一般程式修改：主 Agent 規劃與實作 → 一位 verifier 獨立驗證 → 原實作者定向修正 → 同一 verifier 複驗。
- 大型跨模組或重要需求歧義：才加入 planner；需要獨立實作責任時才加入 implementer。每個角色須有具體交付範圍；工作量大本身不代表必須增加協調層，按獨立工作與交接收益選擇，使用者明確分工優先。
- 一次只有一位 application code 寫入負責人；委派後主 Agent 可做不重疊的工作，不同步重做相同分析、修改或全文審閱。
- Verifier 不得為節省成本降低驗收標準；缺少必要證據就是未完成，不能以省略測試宣稱通過。

## 2. 模型與正確派工

[專案設定](../.codex/config.toml) 的主 Agent、未指定角色之子 Agent，以及三個自訂角色均使用 gpt-6-astra／high；planner、verifier 保持 read-only，implementer 保持 workspace-write。並行上限仍為 4，這只是容量上限，不是啟動數量目標或 token 預算。

- 使用 spawn_agent 時明確指定 agent_type="planner"、"implementer" 或 "verifier"；只設定 task_name 不會選用角色。
- 預設 fork_turns="none"，避免繼承整段開發歷史；交接提供原需求、必要背景、檔案責任、驗收條件、最新 finding 與證據位置。
- 有關聯的修正沿用原角色，followup_task 只在有實質新工作時使用；不要為取得狀態重新啟動角色。
- 派工時核對可用角色定義／回傳資訊的模型與推理強度一次；不可只看角色名稱就認定已套用。無法取得實際設定時如實標示，勿反覆讀取整份執行紀錄。
- 若角色不存在或仍載入舊設定，不用同名預設 Agent 冒充；主 Agent 繼續可完成的工作，交代獨立驗證是否仍待完成。
- 單純協調／問答可由使用者在支援的任務設定選 low／medium；一般開發預設 high。只有已定位的困難推理才考慮 xhigh，記錄原因，不連帶提高所有角色。
- 專案預設不保證覆蓋既有任務／UI 的明確選擇，也不會改寫已啟動子 Agent；重新載入專案設定或開新任務後，仍須核對實際設定。

## 3. 控制讀取與協調成本

先依 [總覽第 1 節](系統規則與知識總覽.md#1-工作前必讀與文件維護) 路由讀取，不重讀未變動全文、不把完整日誌或整個檔案貼進交接。工具先彙整結果，只回傳必要片段；既有證據以路徑及行號引用。

初次派工及後續交接均以約 500 字摘要為目標，必要 finding 不因字數限制省略；共同規則引用既有文件，不重貼整份計畫。派工交代目標、檔案責任、驗收條件、證據位置及阻礙；回報只列完成項目、變更／版本、檢查結果、未解問題與下一步，完整命令及日誌留在證據檔。

主 Agent 的協調摘要只記錄當前階段、責任人、凍結範圍與待決事項；委派期間可繼續其他不重疊工作。使用事件等待並遵守平台的等待與進度更新限制；每次醒來只處理新事件及必要的一句更新，無變化就沿用先前決定，不額外 list_agents、read_thread、催問或重讀背景。followup_task 僅交付新的具體工作；子 Agent 批次回報里程碑與 findings，會影響正在執行作業的重大阻礙立即回報。

同一階段維護一份精簡狀態摘要，沿用既有證據索引；只有狀態、凍結範圍或需驗證的資料改變時才更新相關紀錄，不為例行進度回報重產全工作區快照、交付清單或完整文件。

## 4. 實作收斂、分層驗證及付費測試

- **開始前預檢：** 按任務核對 shell／runtime、必要登入及權限、資源 ID／number、部署參數與既有測試入口；缺項一次列出，使用者須親自登入的部分與可繼續的本機工作分開。保存安全的錯誤階段／代碼，避免包裝器掩蓋診斷；不記錄 Secret。後續外部操作仍依風險重新核對目標。
- **先確認可行性：** 需要模型或外部服務的實際行為時，先完成必要隔離、計數與授權控制，再從既有案例選最小的代表性高風險集合；翻譯例包括人物角色、術語、否定／條件、金額分母及跨句關係。結果支持方案後才擴大實作、評估工具或付費集合；小量檢查不能替代完整驗收，未見案例仍保留給獨立驗證。
- **兩輪未收斂即檢討設計：** 一輪是同一根因類別的修正及獨立複驗；連續兩輪仍漏檢或誤拒時，先暫停該類逐案補丁，由原實作者整理共同根因、正反／相鄰案例、可一般化方案及影響，主 Agent 在既有授權內決定下一步，不自動增派角色或要求使用者重複批准。新版本或 finding ID 不重置同類計數；其他獨立工作可繼續。只有需求／授權／預算需變更時才釐清，驗收門檻及使用者停修限制持續有效。
- **限制工具複雜度：** 評估工具先採最小的原始回應保存、完整請求識別、記帳及防重複執行；確有跨版本沿用需求時，再明定相容條件與最小承接方式，不每輪追加特殊流程。

1. 中間修正先做受影響的離線測試、型別檢查、建置及原始回應重播，同批涵蓋正確輸入、原失敗與相鄰邊界。最終交付／部署候選凍結前完成必要的完整離線檢查及設定預檢；再有影響時重驗相關範圍，部署入口的既有必要檢查不省略，文件／格式／Agent 設定依第 5 節做靜態檢查即可。
2. 若只改輸出檢查、格式還原或字形相容，且送往模型的內容／參數不變，優先重播受影響回應及正反案例；勿僅因候選編號、日期或程式 hash 改變重發全部 API。
3. 若改變送出的原文、提示、保護標記、模型、術語表或參數，舊回應不足以證明新的模型行為；在既有授權內定向呼叫真實 API，必要時擴大。
4. 完整離線檢查依重要風險與交付需要執行；完整付費回歸集中在最終穩定候選且確有必要時執行。再次執行前說明新增改動使哪些證據失效，不例行重跑固定 430 筆或每案三輪。
5. Verifier 獨立核對需求、diff、證據來源並重現關鍵案例；同類 findings 連同正確、錯誤及相鄰邊界一次交接，重大阻礙即時回報。複驗聚焦修正及受影響範圍，不每輪重啟全文審查或固定新增付費案例；新發現照實保留，不因輪次或成本而降低嚴重度。
6. 沿用證據保留原模型／資料集／請求參數／程式版本；新程式的離線重播另記版本。不得把舊回應改標為新候選的真實 API 結果，不修改原始回應或預期來湊通過。
7. 付費 API 只在使用者已授權的範圍與預算內執行；尚無範圍或預算時，先完成可免費完成的部分並提供請求數、含標記的字元數、重試上限及費用估計。已有授權不重複詢問。
8. 接近預算上限、重複失敗或需要擴大範圍時，先停止增加付費呼叫並說明原因與剩餘工作；不以自動增加案例或全量重跑代替定位問題。只有確有缺口才擴充測試。

本流程是 Agent 行為規範，不是程式強制的 token／費用限額；本次未新增計費攔截器或變更 application code。

## 5. 記錄與生效確認

每個主要階段保留一次精簡結果：角色、模型／推理、版本、檢查範圍與結果；用量資料可得時分開記錄未快取輸入、快取輸入及輸出，推理 token 已包含於輸出，不重複加總。API 字元費用與 Codex token 分開核對；不為量測再開額外 Agent。

設定維護只檢查 TOML、相對路徑、角色欄位、文件一致性與 CRLF，不啟動模型驗收流程或付費 API。靜態檢查通過不等於現有任務已重新載入或角色已實際執行。
