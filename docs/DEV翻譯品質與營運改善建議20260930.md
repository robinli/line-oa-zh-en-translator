## 實際問題與影響

以下摘錄只保留判斷所需短語，人名以 A／B 代稱；完整原文及 ID 對照只在 Git 忽略的本機證據中。稅務案例只評估語言忠實度，不判斷來源中免稅主張本身是否正確。

| 案例 | 觀察 | 建議方向 |
|---|---|---|
| 9/28「You called A」 | 譯成「你叫 A」，而前後正在確認是否致電確認郵件 | 保留打電話動作；引用／相鄰語境可協助消歧 |
| 9/28「confirmed with B … @A」 | @A 被放入 B 姓名後的括號，容易誤認為同一人 | 把提及完整性與人物關係分開檢查，不能只驗證標記數量 |
| 9/29 稅則與船公司接受代碼 | 同文從 tariff code 變成 export tax／tax；「可以收」變成 can collect | 稅則／稅號使用 tariff code／HS code，接受代碼與收取稅款須分清 |
| 9/30 稅號 | 譯成 tax ID numbers，變成納稅人識別號 | 新增海關語境的術語與相鄰反例，不把所有稅務 ID 一律改寫 |
| 9/30「follow up on the 30% advance payment today」 | 譯成跟進「今天支付的」30% 預付款 | 保留「今天跟進」而不是替付款加上日期或已付款暗示 |
| 9/26「push to get remaining balance」 | 譯成「努力爭取剩餘餘額」 | 在交易語境應表達催收／爭取收齊尾款 |
| 9/26 container、9/29 櫃門 | 分別譯成容器、cabinet door | 裝櫃語境用貨櫃／container doors，保留其他容器及家具語境 |
| 9/29「Fine」 | 作確認回覆卻譯成「美好的」 | 精確短句對照或有限上下文；不可把所有含 Fine 的句子直接替換 |

## 現行流程的評估

DEV 群組事件經簽章檢查、採集及群組設定後，判斷語言方向，保護提及／代碼／數量等資料，送出翻譯、還原並檢查，最後回覆 LINE。中英採 NMT 加一般術語表，中越採 NMT；中越沒有中英商務語意檢查。相同譯文回覆 👆，失敗回覆 🚧。不自動換引擎、不做品質重試。

優點是單次呼叫便於估算成本，原生提及、數量及代碼有保護，成功與失敗都有可追查路徑，已能用真實 DEV 流量驅動改善。簽章、隔離帳號與逐次帳本亦有清楚邊界。

主要缺口如下：

1. **語意檢查覆蓋有限。** 金額或名稱仍在，不代表人物關係、付款狀態、時間或領域意思正確；本批已看到這些錯誤通過。歷史 v21 未解的「must confirm → 不必確認」等控制案例也未因 9/29 字串保護而獲得品質放行。
2. **沒有跨訊息語境。** 28 則有 quotedMessageId，其中 22 則能在同群資料找到被引用原文，現有翻譯流程未利用。其餘 6 則無法找到，不能猜測內容。
3. **術語表與實際工作有落差。** 現行 17 條中英、32 條英中主要處理價格及商務詞；最近對話已大量涉及稅則、產地證、裝櫃、樣品及產線電力，應按領域補足，避免無限制擴張通用詞。
4. **語言路由是字元判斷。** 中越群的英語 Good night／Good morning 仍標記成越語來源，這批結果可理解，但不能保證其他英越混合句可靠；應先記錄／評估混語比例再設計路由，不直接增加每則付費語言辨識。
5. **觀測資料尚不完整。** 中英有請求字元與耗時，現行中越沒有相同 metric；品質資料缺精確拒絕細碼及每筆計費資訊，本次只能用 trace 關聯。保存原文也未保存完整提及位置契約，無法完全重建歷史請求。
6. **每次翻譯前置工作較重。** 逐次查 token 身分、帳單及服務帳號，再交易更新共同帳本；每個 webhook 又讀全部群組清單，每個事件起始／完成皆寫群組名稱。這些設計有隔離與完整性目的，但增加延遲、讀寫與維護成本。不要在未量測前直接移除防護。
7. **記錄去重不等於翻譯去重。** 本次重複 receipt 是已知合成事件，不能據此宣稱真人重複翻譯；程式仍缺涵蓋處理與送信狀態的事件去重機制，流量增加前值得補齊。

51 次可關聯中英請求的 Cloud Run HTTP 耗時中位數約 3.19 秒、P95 約 7.32 秒；這不是手機顯示時間，且個別 HTTP 請求可能含其他事件。身分查詢及翻譯各自使用逾時，加上資料庫與 LINE，沒有一個共同剩餘時限，建議補端到端期限和階段耗時，而非單純加大 Function 時限。

以 NMT 未扣抵單價計，44,700 字元約 **US$0.894**，manual 約 **US$0.435**。這只是翻譯清單價估值，不是已實付金額，也不包括基礎設施、語音、稅、折扣或其他同帳單用量。Cloud Billing 明細本次未讀取，因此不宣稱完整月帳單為零。

Google NMT 按輸入字元計價，包含 HTML、空白及未翻譯內容；每百萬 US$20，合資格月用量前 500,000 字元以最多 US$10 抵用方式處理。Translation LLM 標準文字翻譯則為輸入與輸出各每百萬 US$10，不能沿用 NMT 免費額度估算。一般 glossary 建立不另收翻譯費。[官方價格](https://cloud.google.com/products/translate/pricing)

## 建議的分階段方案

### 第一階段 建立品質與成本基準

優先度最高，先做最小範圍，API 支出不應因觀測而增加。

- 將本批 58 則語意結果作本機回歸資料；把敏感案例改寫為保留相同語義結構的合成案例，才用於新模型測試。每個問題加一個正確相鄰反例，尤其付款「今天跟進／今天已支付」、稅號「HS code／tax ID」、拉線「接電／牽線」。
- 每筆補上細拒絕碼、計費輸入字元、輸出字元、耗時、是否實際呼叫 API、字串保護命中原因；中越與中英使用一致指標。現行 raw 候選不保存政策維持；先以不含本文的階段診斷改善追查，若日後真的需保存候選，另定存取及保留政策。
- 在開始翻譯前按 webhookEventId 原子取得處理權，狀態區分處理中、已完成、發送不確定；不因去重紀錄逾時便盲目重送 LINE。
- 維持帳本累計不歸零，另加每日／每月服務用量視圖，把測試費與 runtime 分開。先設費用告警的方案，不能把 alerts-only 當硬上限；若要用 Google 新的 spend cap，需另評估服務中断及實際可用性。[告警說明](https://docs.cloud.google.com/billing/docs/how-to/budgets)、[spend cap 說明](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps)

建議驗收：統計可逐筆對帳；真人樣本、合成事件、正常略過分開；同一事件不重複計費；觀測失敗不改變原定翻譯回覆政策。

### 第二階段 用低成本方法改善常見錯誤

- 中英先補約 10～20 個有明確領域的詞組：稅則／稅號、貨櫃／櫃門、催收尾款、預付款等，並加入不應套用的銀行、家具及一般容器反例；不要只做全域輸出字串替換。
- 中越產線另外建立接電、拉電線、機器配線等候選詞組與測試；這是新增領域能力，不能假定既有「中越不載入商務規則」已授權套用中英檢查器。
- Fine 等完整短句可評估經確認的固定譯法，保留上下文歧義；不把所有大寫、產品字串或包含該單字的長句一律略過。
- 對普通連字詞及列表保留提出規則選項，確認後才修改 9/29 行為；原樣代碼、日期、百分比及真正報價仍是硬性契約。
- 把數字／代碼／mention 等硬契約與有限的語意規則分層。新增資料應補到通用的動作、角色及時間關係，不再為每個句子增加一條特殊判斷。

建議驗收：本次 15 筆修正目標逐筆處理或明確保留未知；既有已知 High 控制案例仍須過關；預付款、否定、責任及金額不得有新重大錯誤，不能只讓拒絕率下降。原有停修與付費暫停仍有效，本報告不自動啟動下一輪。

### 第三階段 再評估有限上下文與選擇性模型

以「引用原文優先，其次同群極短最近上下文」開始，設定明確時間及字數限制。只翻當前訊息，不把上下文的新事實寫入譯文；不足就保持模糊，不猜人名／付款／責任。NMT 的多個 contents 是多份翻譯輸入，不能只把歷史加進去就視為真正上下文理解，必須建立可驗證的協定或選擇支援此能力的模型。

可比較：A 為改善後 NMT；B 為有明確上下文界線的一個候選模型。先用約 30～40 個合成問題／反例確認方向，再決定是否擴大；另留未見案例，不能拿本批已知題的修正成果當通用準確率。由於歷史 TLLM 亦有品質限制，不建議只因「是 LLM」便全量換引擎。

如果後續證據支持，只把高風險訊息在呼叫前路由到候選引擎，每則一次生成並接受相同硬契約檢查。高風險可涵蓋付款狀態、責任／否定、稅則、多方提及及依賴引用的短句；此路由仍是新的產品行為，需在既有規則外明確決定，不能當作現行自動 fallback。

以本批平均輸入／輸出格式字元估算，若 10,000 則中有 10% 改走標準 Translation LLM，且沒有增加上下文、重試或回傳量，清單價約 US$44.51，與全 NMT 的 US$44.48 接近；若全部先 NMT、其中 10% 再跑 TLLM，則約 US$48.96。實際上下文、雙次審查及格式會改變費用，必須量測；選擇性使用模型不必然很貴，但也沒有本次實測證明它更好。

建議第一個付費評估方案只準備一個候選、明列請求數及含格式字元：例如 NMT 上限 100,000 輸入字元約 US$2；標準 TLLM 上限各 100,000 輸入／輸出字元約 US$2，均為未抵用估算。這是待決的方案，不是本次執行授權，也不恢復先前已取消的服務累計上限。

### 第四階段 流量增加後再做效能整理

身分與隔離資訊可評估在冷啟動驗證並短時間快取，保留過期／錯誤時停止及權限撤銷測試；token 正常刷新仍交認證庫。群組名單避免每則全掃，群組名稱只在新增／變動时寫；記錄開關仍保持即時生效。先增加階段耗時再定是否值得，不能宣稱本次已量到可節省多少延遲。

只對同群、同語向、同術語／規則版本、相同上下文及提及契約的確定重複訊息評估快取；快取不能跨群混用人物，仍需檢查發送當下的提及條件。現階段優先做事件去重，沒有證據支持先建通用翻譯快取或向量記憶。

## 建議採納的最小方案

先完成第一、二階段，保留 NMT 的單次呼叫與現有資料保護，以實際語意缺陷減少作為成效，再決定第三階段。近期最大的改善收益是降低商務誤解，而不是省掉目前不足一美元的 DEV 翻譯估算費；規模達每月萬則後，字元膨脹、重複呼叫及人工作業才需要一起算完整成本。
