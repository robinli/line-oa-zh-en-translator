# 原文直送翻譯比較評估

日期：2026-09-24。狀態：API 比較與逐句審閱完成；下一版 adapter 尚未實作、尚未部署。正式版本仍為 linewebhook-00018-huk，100% 流量。

## 結論

Google 翻譯的方向可行，但必須一起處理上下文與資料保護。建議下一版保留 Translation LLM 與 v8 術語表，讓模型看到數值、單位及整則訊息的上下文，僅保護必須原樣保留的資料，再做針對性檢查。

本次直接重現了保護標記導致拒絕，以及數值還原成功卻變成「20 kg 個袋子」的問題。單靠放寬標記解碼或取消所有檢查，都不能完整解決。

NMT 將兩段合併成一筆輸入後，三輪都正確保留「小袋做不到，才用大袋」的條件，支持使用者提出的方向；但另有單段案例把 CNF 譯成含稅、底價與基礎價格混為一談，因此本候選尚不適合直接取代現行中英商務流程。此結論不影響現行無商務規則的中越 NMT。

## 範圍與方法

- 30 則固定合成案例：18 則新增包裝／數量／條件案例，加上 12 則既有商務、提及及字面資料回歸案例；每案每流程重複三輪，共 270 個結果。
- 另用兩則多段合成案例，將整則訊息放入單一 contents 元素，比較兩個原文候選各三輪，補測 12 個結果；合計 282 個結果、295 次 API 請求（包含現行流程的品質重試）。
- 沒有把截圖中的真人原文送出；近似文法案例改用 Norva、20 kg、600 kg 等合成資料，也沒有發送 LINE 訊息。
- Node.js 22.23.2。現行基準使用部署快照一致的 candidate-v12 adapter 與既定姓名清單；保留兩次品質嘗試，每次 15 秒，服務錯誤不重試。
- 原文候選保留基本傳輸解碼及繁體轉換，但沒有現行商務守門，也未實作原生提及 occurrence 對應。這些是比較原型，不是可直接上線的完整 adapter。
- 主實驗保留現行逐段處理：每段是同一 API 請求中不同的 contents 元素。補測才是整則文字單一元素，兩者必須分開解讀。
- 逐句審閱由 Codex 進行，涵蓋三輪所有不同譯文；尚未經獨立中英人工驗收。本報告不宣稱整體翻譯準確率。

| 流程 | 模型／設定 | 產生譯文 | 品質拒絕 | 服務錯誤 | API 請求 |
|---|---|---:|---:|---:|---:|
| 現行 | Translation LLM、v8 glossary、既有保護與驗證 | 77 / 90 | 13 | 0 | 103 |
| 原文逐段 TLLM | Translation LLM、相同 v8 glossary、無商務守門 | 90 / 90 | 0 | 0 | 90 |
| 原文逐段 NMT | general/nmt、無 glossary、無商務守門 | 90 / 90 | 0 | 0 | 90 |

產生譯文不代表通過語意或系統需求驗收。原文候選不會因本次發現的語意錯誤而自動拒絕。兩種 TLLM 同用 us-central1；NMT 使用 global、未套術語表，所以比較的是候選流程，不能把全部差異歸因於模型本身。短時間重複同一測試集不代表長期穩定性。

## 漏翻及格式問題的重現

合成例：

~~~text
If you can make 20kg bags is better. With norva name.

If can't make put in FIBC bulk bag. 600 kg each bag
~~~

現行流程將重量轉為 Quantity… 標記。第一輪其中一筆回傳為「每袋數量：KSRAABQX」，而現有解碼僅容許「Quantity識別碼」或「數量 識別碼」等形式，不接受插入冒號或將識別碼移到「數量」之前。近似口語包裝案例三輪皆 protected_value_changed；另一個分段包裝案例有一輪同樣因標記順序改變而拒絕，共 4 次。

另三則中文公斤案例，各三輪均 unprotected_trade_data，共 9 次。單位辨識包含 KG／MT 等縮寫，未把「公斤」與數字一起保護；翻成 kg 後又被當成新增的未保護單位。這是合法翻譯遭到拒絕的具體例子。

已產生譯文中仍可見「20 kg 個袋子」「20 kg 數量的袋子」，以及把 FIBC 放到小袋上的情況。隱藏重量的語意後，再把原值放回標記，不能保證重量與包裝的關係正確。

以上原因由本輪合成請求／回應直接重現，不能反推歷史真人訊息必定發生完全相同的字元變形。歷史日誌沒有保存原文與譯文。

## 上下文補測

| 兩段包裝例 | 結果（三輪） |
|---|---|
| 原文逐段 NMT | 都把第二段條件理解成「無法裝入噸袋／貨櫃袋」；兩輪另出現 FIBC 貨櫃 |
| 原文整則 NMT | 都保留「小袋做不到，才用大袋」及兩種重量，維持兩段 |
| 原文逐段 TLLM | 都保留主要備案條件及重量，維持兩段 |
| 原文整則 TLLM | 都保留主要備案條件及重量，但合併成一段 |

整則 NMT 的代表輸出：

~~~text
如果可以的話，最好分裝成 20 公斤的袋子，並貼上 Norva 的標籤。

如果分裝不了，就裝進 FIBC 噸袋，每袋 600 公斤。
~~~

此例的數量與備案關係已改善，但「With norva name」未明示貼標方式，譯成「貼上…標籤」仍有具體化原文的成分；品牌大小寫也改變。這不能視為所有嚴格商務規則都通過。

另一個三段案例中，整則 TLLM 三輪亦全部合成一段，NMT 三輪保留三段。下一版如改用整則輸入，需另驗證能保持上下文的段落結構，例如 HTML 區塊；本輪沒有驗證該新實作。

## 原文候選仍需修正的部分

| 問題 | 原文 TLLM | 原文 NMT |
|---|---|---|
| 包裝條件與數量 | 多數包裝例改善；禁止計算三輪變成「無需計算」 | 完整上下文改善口語備案；另一單段 FIBC bags 三輪錯成貨櫃 |
| 中英術語 | 此批底價、成本價、出廠價、CNF 等搭配 v8 glossary 正常 | 底價與基礎價格皆 base price；CNF 變含稅，與後句不含稅衝突 |
| 名稱與提及 | 中文提及名稱被翻譯，沒有原生提及位置對應 | 另有姓名音譯，沒有原生提及位置對應 |
| 字面 entity | glossaryTranslations 分支已改動文字；候選解碼又改動字面 entity | API 原文仍有字面 entity，但候選解碼將其當傳輸資料，造成改動 |
| 原樣格式 | kg／USD 可譯成公斤／美元；須明確區分語意相同與字串不變 | 同樣問題，另有 FIBC 縮寫消失、MT 僅寫成噸 |

entity 案例顯示，直接移除既有保護後，不能原封不動套用原本「還原保護值之前」的解碼器。此處是整條處理流程的問題，不能全部算成模型翻錯。

本輪僅在評估時將 kg → 公斤、USD → 美元與真正數值／幣別／單位改變分開看待；正式版的字串保留規則尚未調整。數量檢查也不能只比對數字集合，因相同數字仍可能被放到不同包裝或不同責任人上。

## 建議的下一個開發範圍

1. 建立候選 adapter，保留 Translation LLM、v8 glossary 及既有單一 LINE／Cloud Run 入口；整則訊息保留上下文，同時設計可驗證的段落與原生提及對應。
2. 數值與單位讓模型可見，另建立來源紀錄；將公斤／kg 等同義表示與磅、公噸、袋數區分，檢查正負號、小數、幣別、每袋重量、淨毛重及重複數值的歸屬，禁止自行計算或換算。
3. 精確保護提及身分、必要姓名、產品碼、網址／郵件及字面 entity；保留 CNF 等術語及必要商務驗證，避免把所有詞彙都改成不可讀標記。
4. 補上本次發現的「do not → 無需」及包裝角色反轉回歸案例，細分拒絕原因。正式日誌記錄不含聊天內容的原因與統計，不記真人原文。
5. 跑既有回歸、本輪案例及新未見案例的三輪比較，逐句核對語意、提及及段落；通過後才做正式接入與部署驗證。不能用 90/90 有輸出當作放行條件，也不加入自動 NMT fallback。

下一版尚未實作。中越、指令、私訊僅 /我的ID、Firestore 設定及相同譯文不回覆規則均未修改。
