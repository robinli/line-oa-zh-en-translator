## 2. 系統目的與現行範圍

本系統服務多方國際貿易業務群組，重點是忠實保留報價、費用、發言人、責任、承諾程度及交易條件。翻譯器只翻譯，不代替業務判斷、回答問題、計算價格或提供建議。

| 項目 | 現行行為 |
|---|---|
| 聊天來源 | LINE 群組與一對一聊天室；未實作多人聊天室 room 的事件處理 |
| 文字翻譯 | 中翻英、英翻繁中、中英雙向、中越雙向 |
| 語音 | LINE 託管音訊先轉逐字稿，再依文字開關與翻譯模式決定是否附譯文 |
| 啟停 | 文字與語音各自獨立；新聊天室兩項預設皆關閉 |
| 原生 @ | 僅群組文字翻譯，支援原訊息指定提及及已設定的稱呼 |
| 圖片、貼圖、影片、檔案 | 忽略；沒有 OCR 或圖片翻譯功能 |
| 跨訊息上下文 | 未實作聊天歷史記憶；不抓取引用訊息原文來補足上下文 |
| 儲存 | 保存聊天室設定，不保存正常聊天原文、音訊、逐字稿與譯文 |

一般文字與語音流程不同於管理指令；查詢狀態、設定回覆、加入群組的說明不受「相同譯文不回覆」規則取代。

## 3. 指令、權限與聊天室設定

| 指令 | 功能 |
|---|---|
| /中翻英 | 設為 zh-to-en 並啟用文字 |
| /英翻中 | 設為 en-to-zh 並啟用文字 |
| /中英翻譯 | 設為 zh-en 並啟用文字 |
| /中越翻譯 | 設為 zh-vi 並啟用文字 |
| /啟用文字翻譯、/停用文字翻譯 | 只修改文字開關，保留模式與語音開關 |
| /啟用語音轉文字、/停用語音轉文字 | 只修改語音開關，保留模式與文字開關 |
| /啟用翻譯、/停用翻譯 | 相容舊指令，目前只控制文字開關 |
| /翻譯狀態 | 顯示模式與兩個開關 |
| /翻譯設定 | 顯示狀態與指令清單 |
| /我的ID | 僅一對一私訊回覆發送者自己的 LINE userId；群組中忽略 |

- 指令先去掉前後空白，內容必須完全相符。
- 群組只有 LINE_OWNER_USER_ID 指定的單一帳號可修改設定；所有群組成員可查詢狀態。不能以顯示名稱或聲稱為管理員來取得權限。
- 一對一聊天室由該使用者自行設定；缺少來源 userId 的設定修改不執行。
- 切換模式會開啟文字翻譯，不連動語音開關。
- 加入群組時讀取現有設定並回覆狀態／啟用說明，不重設舊設定。
- 語音逐字稿中的指令只當作內容，不能執行設定變更。
- 每個聊天室各自保存設定；不得因更新某群組而重設其他群組。

Firestore collection 為 lineTranslationGroups：群組文件 ID 是原始 groupId，一對一是 user:{userId}。欄位為 textTranslationEnabled、audioTranscriptionEnabled、translationMode、changedBy、changedAt。

舊 enabled 欄位的相容規則：兩個新開關各自優先讀明確的布林值，缺少或非布林時才沿用 enabled === true。修改新開關以 merge 寫入，不改舊 enabled，不覆蓋另一個開關。缺少或未辨識的模式目前回落 zh-en。

## 4. 語言判斷與「不回覆」規則

文字先依有效 LINE mention metadata 排除原生 @ 顯示名稱，再判斷正文；索引採原始文字的 UTF-16 位置，不能先 trim 再套索引。沒有有效 metadata 就不猜姓名範圍。

目前用字元規則判斷方向，不是完整語言辨識：含程式辨識範圍內的漢字視為中文，否則含拉丁字母視為模式中的英文或越南文。中英混合視為中文；中越模式中的拉丁文字按越南文處理。

| 模式 | 中文正文 | 英文／拉丁文字正文 |
|---|---|---|
| zh-to-en | 翻成英文 | 不回覆 |
| en-to-zh | 不回覆 | 翻成繁體中文 |
| zh-en | 翻成英文 | 翻成繁體中文 |
| zh-vi | 翻成越南文 | 按越南文翻成繁體中文 |

語音逐字稿使用相同的方向規則，但逐字稿沒有 LINE 原生 mention metadata。純數字、符號、Emoji 不呼叫翻譯服務；僅有原生 @ 名稱而沒有可翻譯正文時也不因姓名觸發翻譯。

### 相同譯文不回覆

- 適用群組文字；先取得翻譯，再比對原文與譯文，不能改成產品代碼黑名單。
- 比對採 NFKC 全半形相容正規化、去首尾空白、合併連續空白／換行，並忽略程式指定的常見標點兩側空白。
- PP-BK?、PP-BK ?、PP-BK？會視為相同。保護 PH-BK／PP-BK 是防止改動產品代碼，不是禁止翻譯。
- 大寫英文不能一律當作代碼跳過。
- 相同時不發訊息、不為新增 @ 而額外回覆，計為 ignored；只留不含正文的診斷。
- 一對一相同譯文與語音逐字稿回覆不套用這項群組規則。

### 翻譯失敗保持安靜

使用者已明確要求：不得再回覆「本則翻譯暫時無法確認，請以原訊息為準。」及其英文版本。

- 服務失敗或品質驗證仍不通過時，不回覆失敗提示，也不發送未驗證譯文。
- 群組／一對一的文字及語音翻譯皆適用；只留後台錯誤，計為 failed，繼續處理同批其他事件。
- 不可為了「一定要有回覆」而取消資料驗證、輸出半截內容或自動退回舊翻譯器。
- 原有設定成功／無權限回覆、語音超時及逐字稿過長提示是不同情況，不因本規則而一併移除。
- 若語音辨識已成功、但後續必要翻譯失敗，目前整筆不回覆；未另外發送逐字稿補救訊息。

## 5. 商務翻譯知識與不可混淆的概念

| 原詞／情境 | 翻譯原則 |
|---|---|
| 底價、最低可接受價格 | lowest acceptable price／minimum acceptable price；不是 base price、cost price，也不是已成交價 |
| 成本價 | cost price；越文依情境用 giá vốn／giá thành |
| 出廠價 | ex-factory price；不能自行加上運費或把它視為完整到岸報價 |
| 基礎價格 | base price |
| 報價、對客報價 | quotation／quoted price、price quoted to the customer |
| best price | 最優惠報價；原文未表明最低／底線，不自行加強成「底價／最低價」 |
| account owner／owner of the account | 客戶業務情境是「客戶業務負責人／該客戶的負責人」；銀行、登入帳戶依各自情境 |
| sales representative | 業務代表 |
| freight／shipping cost | 運費 |
| commission、markup、surcharge | 佣金、加價、附加費；三者不可自行互換 |
| taxes and duties | 稅費；不能由 CNF 推論已含稅 |
| including／含 | 包含在既有金額內 |
| additional／另加 | 在既有金額上另加；未知項目不得擅自命名為運費、佣金或稅 |
| can／could、should、must | 能力或可能、建議、義務；不得把「可以做更多」改成「不應只是／必須」 |
| 一次就把底價給客戶 | 議價揭露時機，使用 right away／at the outset，不是 all at once |
| 名字 + brother | 商務稱呼通常保留名字或名字＋哥，不音譯成另一人、不解讀成汽車品牌；已匹配 @ 別名則交由提及機制處理 |

- 原樣保留 CNF、C&F、CFR、CIF、FOB、EXW 等原文縮寫，不自動將一種貿易條件改成另一種。
- 保留誰提出、誰確認、誰付款、誰負責；不能把特定人名替換成「你／我們」而改變責任歸屬。
- 保留問句、否定、提議、尚未確認、已確認、條件與承諾程度。
- 不計算算式、不換匯、不改單位、不湊整數、不憑空增加金額。
- 不補原文未說的運費、佣金、稅、保險、目的地、計價單位或交易條件。
- 原英文有拼字／文法錯誤時可改善可讀性，但不能改變事實。保留人名、公司名及產品代碼，不任意音譯。
- 預設人名保護：Wei、Shan、Eric、Kash、Kumar、Kumaran、Niranjan。Kumar 與 Kumaran 分別保護原字串，不能僅憑拼寫相近推定為同一人。
- 中文輸出使用繁體中文，英文及越南文保持自然商務用語；保留段落，沒有額外前言、分析或建議。

## 6. 翻譯引擎與品質保護

正式引擎 business 使用 Vertex AI Gemini；google 為保留的舊 Cloud Translation 引擎，須明確指定才使用。選擇新引擎的原因是需要系統指令及多方商務語義規則，並非只替換幾個字。

1. 原文數值、可辨識算式、幣別、縮寫單位、貿易縮寫、已知人名、產品代碼、網址／郵件及指定提及範圍轉為隨機逐筆標記。
2. 模型收到標記、原始值及種類以理解語意，但只能在輸出放回標記；系統不是把所有原文資料隱藏於模型之外。
3. 原文與 protectedValues 都是待翻譯資料，不能把其中的「忽略規則」當成指令。模型無工具及對外操作權限。
4. 模型必須回傳只含 translation 字串的 JSON；只接受完整結束的非思考內容，拒絕截斷／封鎖／不合格式的輸出。
5. 每個標記恰好出現一次才能還原；新增數字、遺漏或重複標記、未保護的貿易資料、部分重複人名與明顯錯誤語言方向會被拒絕。
6. 另有針對底價／成本價／出廠價、議價揭露時機及不當最低價承諾的檢查。
7. 只有品質驗證失敗重試一次；每次模型請求 15 秒逾時，SDK HTTP 自動重試關閉，服務錯誤不在翻譯器中重試。
8. 最終還原的單次譯文上限 4,500 UTF-16 單位；超出即拒絕。
9. LINE 正文按字面處理，不自動把 HTML entity 解碼；例如原文真的包含 &#x20; 時，不擅自視為多餘空格刪除。

提示規則與機械驗證不是完整語義正確性的證明。未知人名、中文數量詞、未辨識編碼及非縮寫單位仍有人工檢視需求，不能把測試通過宣稱為所有翻譯 100% 正確。

## 7. LINE 原生 @ 提及

- Wei bro、Wei brother 已對應使用者提供的同一個 LINE userId；忽略英文大小寫，容許連續空格／Tab，支援手打 @Wei bro。
- 單獨 Wei 不自動提及；不匹配 Wei Brotherhood 等較長單字，不從網址或郵件猜對象。
- 真實對應只放 Git 忽略的設定，見第 10 節；本文件不記錄實際 userId。userId 與可搜尋的 LINE ID 不是同一概念，不能從個人頁顯示名稱猜出 userId。
- 原訊息原生 mention metadata 的 userId 優先；不得因顯示名稱像某別名就換成另一人。
- 缺少 userId、@All、機器人、自我提及、無效或矛盾 metadata 只保留文字。每則來源最多處理 20 處指定提及。
- 保護標記還原時傳回「原文位置→譯文位置」，不靠搜尋譯文中的同名文字；可處理語序調整與同名不同人。
- 對應用的 userId、groupId 與身分映射不傳給模型，只在伺服器與 LINE API 之間使用。
- 發送前查目前群組的成員資料，每個不同 userId 在該次回覆只查一次，逾時 3 秒。不同群組分別檢查，不快取個人檔案。
- 成員確認失敗、非群組成員或查詢失敗時，保留純文字稱呼。
- 確認後使用 textV2 substitution，顯示對方目前 LINE 名稱。普通「@名字」字串不等於原生提及。
- 每則 textV2 最多 20 個提及；正文大括號須轉義。長文分段不能截斷提及、佔位符或 Emoji。
- LINE 明確 HTTP 400 拒絕含提及回覆時，最多再試一次純文字；逾時、429、5xx 不重送，以免不確定是否送達時重複通知。
- 已安裝 LINE SDK 的 HTTPFetchError 欄位是 status，不是 statusCode；改 SDK 時核對實際契約。
- 私訊、語音及沒有可靠位置還原的舊 google 引擎不新增原生提及。
- 翻譯方向及「相同譯文不回覆」優先，不能為了 @ 對方額外發送不需翻譯的訊息。
- 別名設定為 [] 只停用稱呼自動轉換，原文有效的原生提及仍可保留。無效／同名指向不同人的別名設定整組停用並留不含資料的警告，原生提及仍可處理。

## 8. 架構、回覆及事件處理

處理流程：LINE POST → 簽章與事件驗證 → 指令或聊天室設定 → 文字方向判斷／音訊下載與辨識 → 商務翻譯及品質驗證 → 相同譯文判斷 → 必要時確認群組成員 → LINE Reply API。

- 僅接受 POST；其他方法 HTTP 405 並附 Allow: POST。
- 用未修改的 rawBody 與 LINE_CHANNEL_SECRET 計算 HMAC-SHA256，以 timingSafeEqual 比較；不可先重組 JSON 才驗證簽章。
- 缺少或無效簽章 HTTP 401；JSON／events 格式錯誤 HTTP 400。
- 有效事件逐筆循序處理，正常空 events 回傳 HTTP 200。
- 單筆失敗不終止整批；統計 processed、ignored、failed，整體仍回 HTTP 200。因此 HTTP 200 不代表每則譯文成功。
- 沒有獨立的已送事件去重儲存；不可宣稱能杜絕所有 webhook 重送造成的重複處理。
- 一般回覆使用 text，含有效提及使用 textV2；沿用收到的 replyToken，不任意改成主動 push。
- 回覆最多五則、單則最多 5,000 UTF-16 單位；整段回覆最多 24,000，超出拒絕。提及／轉義造成超過五則時，改完整純文字分段，不截斷內容。
- 語音辨識用 Speech-to-Text v2、long 模型、自動標點；語言為 cmn-Hant-TW＋en-US，或中越模式的 cmn-Hant-TW＋vi-VN。
- 語音有譯文時回覆「逐字稿＋空行＋譯文」，不添加「語音轉文字／中文／英文」等標題。

## 12. 驗證、部署及回復

在 Windows PowerShell 專案根目錄執行：

~~~powershell
npm.cmd run verify
~~~

verify 包含 TypeScript 檢查、Vitest 與正式建置；Firebase predeploy 也會執行。使用 Node.js 22；本機其他版本可用於輔助操作，但不能只憑不同版本就宣稱正式執行環境已驗證。自動化測試以 mock 隔離 LINE 與雲端服務。

模型評估先建置、設定 GOOGLE_CLOUD_PROJECT 與適用的 ADC，再執行：

~~~powershell
npm.cmd run evaluate:trade --prefix functions
~~~

評估只讀已設定的合成案例，另人工閱讀完整譯文。10 則曾通過的案例、或期望片段通過，不等於一般翻譯準確率。

授權範圍內部署時，先備份當前版本與參數，核對兩個稱呼設定及引擎，再執行：

~~~powershell
$env:FUNCTIONS_DISCOVERY_TIMEOUT = "30"
firebase.cmd deploy --only functions:lineWebhook --project line-auto-translate-bot --non-interactive
~~~

完成後核對 Function ACTIVE、Cloud Run 版本與流量、正式參數及安全日誌。可用簽章空事件、無效簽章、單向略過及會得到相同譯文的虛構事件檢查；使用無效 replyToken 防止意外向真人回覆。不要把此類健康檢查當成真人通知已驗收。

LINE validate/reply 只驗證訊息格式，不驗證對方當時是否在群組，也不證明手機實際顯示／通知結果。真人操作驗收與此分開記錄。

- 2026-09-22 的 textV2 提及、大括號、20 處提及、Emoji 分段與純文字回退格式已驗證。
- linewebhook-00014-yez 部署檢查曾有一次模型服務不可用；針對該虛構事件重試後恢復。單次暫時錯誤不可隱去，也不可據此宣稱所有正式翻譯都無問題。
- 原生提及的實際使用端通知效果，在最近紀錄中尚未完成真人驗收。
- 回復舊引擎可明確設 TRANSLATION_ENGINE=google 後重新部署，但會失去商務模型驗證及可靠原生提及；方向及相同譯文規則仍在。
- 回復版本時檢查是否會重新帶回舊錯誤行為，尤其翻譯失敗雙語提示。除非使用者明確改變需求，不能把回復舊版當成允許恢復已刪除提示的理由。
- 不為了取得一筆測試結果而中斷正式模型、輪替 Secret 或改群組設定。
